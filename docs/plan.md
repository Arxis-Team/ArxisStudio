# ArxisStudio — план разработки (v1)

> Статус: согласован 2026-08-24. Разработка начинается по команде «приступай».

ArxisStudio — кроссплатформенный «движок разработки ПО»: Unity, но для прикладных
приложений. Референс UI — мокап `ArxisStudio.dc.html` (Claude Design, проект
`9b997186-4b89-4743-b752-1d385beb684a`): три экрана — Welcome, Editor, Run/Debug,
тёмная и светлая темы, JetBrains-подобная стилистика. Полная выжимка дизайна —
токены обеих палитр, шрифты, метрики, иконография, анимации, инвентарь экранов —
в [design-spec.md](design-spec.md); это входные данные M0.

## Стек

- .NET **net10.0**, **Avalonia 12.1.x** (мокап упоминает «Avalonia 11.3 / net9.0» — это
  декоративный текст, не требование).
- Текстовый редактор XAML — **AvaloniaEdit**.
- Отладка интерфейса самой студии — **AvaDevTools** (Debug-only, с конечной точкой MCP
  на петле): [devtools.md](devtools.md).
- Существующие и новые базовые библиотеки подключаются как **git-субмодули** с ProjectReference:
  - `ArxisStudio.Markup` — lossless XAML DOM, загрузка живых объектов, round-trip;
  - `ArxisStudio.ProjectSystem` — модель solution, MSBuild-операции, NuGet, watcher,
    адаптер `ProjectSystem.Markup.Xaml` (даёт `XamlLoadEnvironment`);
  - `ArxisStudio.DesignEditor` — канва: viewport, выделение, snapping, направляющие
    (сейчас net8.0 — при интеграции поднять до net10.0);
  - `ArxisStudio.Controls` — **новый репо**: библиотека контролов студии (см. ниже);
  - `ArxisStudio.Themes.Arxis` — **новый репо**: тема студии (dark/light по токенам мокапа).

## Согласованные решения

| Вопрос | Решение |
|---|---|
| Editor-код в проекте пользователя (Unity `Editor/`) | **Не в v1.** Только внешние плагины; SDK проектируется так, чтобы project editor-код добавлялся позже без слома |
| Изоляция расширений | **In-proc**, каждый внешний плагин в collectible `AssemblyLoadContext` |
| Модульность студии | **Всё через общий SDK-контракт, два способа загрузки**: встроенные модули (панели студии) — прямые ProjectReference в default ALC, ноль оверхеда; внешние плагины — collectible ALC с выгрузкой. Код модуля переносим между режимами без изменений |
| Стиль SDK | **Атрибуты, как Unity**: `[Command]`, `[ToolWindow]`, `[CustomInspector]`, `[PropertyDrawer]`, класс-наследник `ToolWindow`. Пункты меню объявляются манифестом, а не атрибутом: меню студия строит, не загружая сборку |
| Докинг | **Свободное дерево, как в Unity**: узел — n-арное деление (ряд/столбец) либо группа вкладок; панели собираются во вкладки, группы отрываются в окна. Движок — `src/ArxisStudio.Docking`, и ссылок на `Sdk`/`Shell`/`Extensibility` у него нет: дерево хранит идентификаторы, живые контролы держит студия и снимает их по `Unloading`. Документы **не выделены типом** — выделен указатель на группу, куда они открываются. Раскладка общая для студии + именованные наборы, отдельным файлом с версией формата |
| Скоуп v1 | **Welcome + Editor**. Экран Run/Debug (runtime-агент, watch, hot reload) — этап 2. В v1 — сборка через ProjectSystem и простой запуск процесса с логом stdout в Console |
| Новые библиотеки | Проекты **внутри главного репо** (`src/`); выделение в отдельные репо — позже, когда API устоится |
| Шаблоны проектов | **Не пишем свои**: обнаруживаем установленные `dotnet new` шаблоны (template engine), создаём проект через них; Avalonia-шаблоны — через `dotnet new install Avalonia.Templates` |
| Плагины v1 | Менеджер с **локальной установкой** (папка/zip с манифестом), вкл/выкл, список установленных. Онлайн-каталог — этап 2 |
| Типы проектов | **Avalonia desktop**. Любой .sln открывается через ProjectSystem, но дизайнер и запуск гарантируются только для Avalonia |
| Язык UI | Как в мокапе (англ. термины панелей + русский текст) поверх **i18n-каркаса** с первого дня |
| XAML-вкладка | **Да**: Design / XAML / Split на AvaloniaEdit с двусторонним round-trip через Markup; подсветка без IntelliSense |
| Learn | Статические ссылки на документацию; курс с прогрессом — позже |
| Контролы и темы | Пара **ArxisStudio.Controls + ArxisStudio.Themes.Arxis** (отдельные репо-субмодули), по образцу Avalonia.Controls / Avalonia.Themes.Fluent. Плагины строят UI **только на Ax\*-контролах** — как в Unity |
| Устройство Controls | **Наследники Avalonia-контролов** (`AxButton : Button`, …) со своими шаблонами + чисто IDE-шные контролы с нуля (сегменты, toolbar, поле свойства, tool-window chrome, дерево) |
| Запрет голых Avalonia-виджетов | Layout-панели Avalonia разрешены; виджеты — только Ax\*. Контроль: **Roslyn-анализатор в SDK** (ошибка/предупреждение при сборке плагина) + предупреждение хоста при загрузке |
| API субрепозиториев | **Можно менять.** Библиотеки из субмодулей (Markup, ProjectSystem, DesignEditor, Controls, Themes.Arxis) — не замороженные зависимости: если интеграции нужен новый или изменённый публичный API, правим его прямо в субмодуле (соблюдая правила репозитория: тесты публичной поверхности, ADR, границы ответственности) и коммитим в его репо |

## Состав решения

```
ArxisStudio/                        ← главный репо (Avalonia-приложение + новые библиотеки)
  external/                         ← git-субмодули
    ArxisStudio.Markup/
    ArxisStudio.ProjectSystem/
    ArxisStudio.DesignEditor/
    ArxisStudio.Controls/           ← новый репо: контролы студии (Ax*)
    ArxisStudio.Themes.Arxis/       ← новый репо: тема студии (dark/light)
  src/
    ArxisStudio.Sdk/                ← контракт расширяемости (аналог UnityEditor API)
    ArxisStudio.Extensibility/      ← хост плагинов
    ArxisStudio.Docking/            ← движок докинга: дерево областей и вкладок
    ArxisStudio.Shell/              ← каркас окна: темы, меню, настройки, i18n
    Modules/                        ← встроенные модули студии
      ArxisStudio.Modules.Sample/   ← образец: панель, команда и служба
    Plugins/                        ← внешние плагины, живущие в этом репозитории
      Arxis.HelloPlugin/            ← образец внешнего плагина
    ArxisStudio/                    ← оболочка: Welcome, раскладка, вкладки
  tests/
```

### ArxisStudio.Controls (отдельный репо)

Библиотека контролов студии — то, из чего строится весь UI ArxisStudio и плагинов,
аналог `Avalonia.Controls` в экосистеме Avalonia. Плагины **не используют** голые
Avalonia-виджеты — как в Unity, где редакторный UI строится только из контролов Unity.

- Основной приём — наследники Avalonia-контролов со своим API и своими theme-ресурсами:
  `AxButton`, `AxTextBox`, `AxCheckBox`, `AxComboBox`, `AxToggleSwitch`, `AxSlider`,
  `AxTabControl`, `AxListBox`, `AxTreeView`, `AxScrollViewer`, `AxMenu`…
- Чисто IDE-шные контролы с нуля: `AxSegmentedControl` (Design/XAML/Split, Dark/Light),
  `AxToolBar`, `AxToolWindowChrome`, `AxPropertyField`, `AxSearchField`, `AxBadge`,
  `AxToolbarToggle`, `AxStatusBar`, `AxColorSwatch` и т.п.
- Layout-примитивы Avalonia (Grid, StackPanel, DockPanel, Border…) разрешены как есть.
- Контролы lookless: шаблоны и цвета живут в теме, не в контроле.
- Набор растёт по потребностям экранов студии; в репо — gallery/demo-приложение.
- Зависимости: только Avalonia.

Контроль запрета: Roslyn-анализатор (поставляется с SDK) — диагностика при использовании
Avalonia-виджетов в коде/разметке плагина; хост при загрузке плагина может предупреждать.

### ArxisStudio.Themes.Arxis (отдельный репо)

Тема студии, аналог `Avalonia.Themes.Fluent`: ControlTheme-шаблоны для всех
Ax*-контролов + палитры **dark/light по токенам мокапа** (`--bg1…bg4`, `--brd`,
`--fg…`, `--acc`, `--sel`, семантические цвета) как Avalonia-ресурсы с переключением
варианта темы. Зависит от ArxisStudio.Controls. Позже возможны альтернативные темы.

### ArxisStudio.Sdk

Только контракт, без реализации. Плагины ссылаются на него, на ArxisStudio.Controls
и на Avalonia (layout). Публичная поверхность SDK в сигнатурах использует Ax*-контролы.

- Атрибуты: `[Command("…")]`, `[ToolWindow("…")]`, `[CustomInspector(typeof(T))]`,
  `[PropertyDrawer(typeof(T))]`, `[ToolWindow(...)]`.
- Базовые классы: `ToolWindow`, `InspectorEditor`, `PropertyDrawer`.
- Roslyn-анализатор «только Ax*-виджеты» — поставляется вместе с SDK.
- Фоновые задачи — `IStudioContext.Tasks`: работа уходит с потока интерфейса, её
  имя и ход видны в строке состояния, отмена общая; сбой идёт через шов, а перед
  выгрузкой плагина его задачи останавливаются.
- Языки студии — словари `lang/<код>.json`: встроенный ресурс, файл рядом со
  студией, установленный языковой пакет (`contributions.languages`), файл в
  `%APPDATA%/ArxisStudio/lang/`; позднее сильнее, наложение поключевое,
  непереведённое падает в английский.
- Настройки плагина — `IStudioContext.Settings`: ключи объявляются в манифесте,
  значения лежат в двух областях (пользовательская —
  `%APPDATA%/ArxisStudio/plugin-settings.json`, проектная — `.arxis/settings.json`
  в проекте), проектное значение перекрывает пользовательское.
- Сервисы (получаются через `IStudioContext`): `ISelectionService`, `IWorkspaceService`
  (обёртка над ProjectSystem-снапшотом), `IDocumentService`, `ICommandService`,
  `IUndoService`, `ILogService`, `ISettingsService`.
- **Точки расширения без UI** (невизуальные плагины/модули):
  - `StudioService` — сервис плагина с жизненным циклом Start/Stop, регистрируется
    атрибутом (аналог `[InitializeOnLoad]` в Unity) и contribution `services`;
  - события-хуки студии: открытие/закрытие проекта, открытие/сохранение документа,
    до/после сборки, изменение выделения, изменения файлов (watcher ProjectSystem);
  - `IBackgroundTaskService` — фоновые задачи с отменой и прогрессом; прогресс и
    уведомления идут в стандартные слоты студии (статус-бар, тосты, Console) — плагин
    без собственного UI остаётся видимым пользователю;
  - события активации для этого: `onProjectOpened`, `onFileSaved:<ext>`, `onBuild`, …
- **Визуальное и невизуальное свободно совмещаются**: «тип» плагина не существует —
  плагин есть набор contributions, и один манифест может объявлять и фоновый сервис,
  и панели, и команды (пример: git-плагин = watcher-сервис + окно лога + команды).
  Части одной сборки разделяют состояние напрямую; ленивая активация — по объединению
  событий активации. Правила общие: UI-поток не блокировать (фон — через
  `IBackgroundTaskService`), правки документов — транзакциями `IUndoService`.
  Плагин-библиотека, публикующий API для других плагинов, требует зависимостей
  плагин-от-плагина — этап 2.
- Модель манифеста плагина.

Соответствие Unity-практикам:
- **Tools Engineering** → `[Command]` + пункт меню в манифесте + `ToolWindow` + сервисы;
- **Editor Extensibility** → contributions плагина: меню, tool windows, типы документов;
- **Custom Inspecting / Property Drawing** → `[CustomInspector]` (замена инспектора для
  типа контрола) и `[PropertyDrawer]` (редактор значения для типа свойства);
- **Plugin Development** → манифест + локальная установка + вкладка Plugins.

### ArxisStudio.Extensibility

- `plugin.json`: id, name, version, publisher, требуемая версия SDK, entry-сборка,
  **декларативные contributions** (commands, menus, toolWindows, languages, settings) и
  **события активации** (`onCommand:…`, `onFileType:…`, `onToolWindow:…`, `onStartup`).
  Формат каталога и манифеста — в приложении A.
- Два режима загрузки за одним контрактом:
  - **встроенные модули** — default ALC, прямые ProjectReference, без изоляции;
  - **внешние плагины** — collectible ALC с выгрузкой (отключение/обновление без
    рестарта студии).
- Ленивая активация: меню и списки хост строит по манифесту, не загружая сборок;
  сборка плагина грузится при первом событии активации. Ленивость распространяется и
  на встроенные модули (Hierarchy активируется при открытии проекта, а не на старте).
- Дистрибутив внешнего плагина — каталог, упакованный в zip с расширением
  **`.axplugin`**; установка = распаковка в папку плагинов, удаление = удаление папки.
  Состояние вкл/выкл — в настройках студии, каталог плагина после установки неизменяем.
- MSBuild-таргет упаковки для авторов плагинов (`src/ArxisStudio.Sdk/build/
  ArxisStudio.Sdk.targets`): на каждой сборке раскладывает выход в формат каталога,
  по просьбе пакует его в `.axplugin` (`AxPluginPack`) и кладёт прямо в папку
  плагинов для отладки (`AxPluginDeploy`). Общие контракты (Sdk, Controls,
  Avalonia) в `bin/` не попадают — список тот же, что у резолвера, — а положенные
  руками замечаются: `AXP0001` о файле с копированием в выход, `AXP0002` о том, что
  всё-таки оказалось в `bin/`. Ошибками кончаются пропавший манифест (`AXP1001`),
  разошедшиеся `entry` и имя сборки (`AXP1002`), выкладка с неизвестным
  идентификатором (`AXP1003`), контрактом объявлена сама entry-сборка
  (`AXP1005`) и объявленный контракт, не доехавший до раскладки (`AXP1006`). Пока SDK поставляется ProjectReference-ом, таргет
  импортируется строкой; с пакетом SDK он подхватится сам — оттого и лежит в
  папке `build/`.
- Сделаны шаги 1 и 2 зависимостей плагин-от-плагина (записи 35, 36): манифест,
  граф, каскад, служба соседей, контрактные сборки и экспорты. Также
  (`dependencies`), подпись/доверие пакетов.
- Резолвер: общие контракты (Sdk, ArxisStudio.Controls, Avalonia) всегда из
  default-контекста — одна идентичность типов, без дублей в памяти.
- Сканирование атрибутов с кэшем между запусками; активация/деактивация; изоляция
  ошибок (упавший плагин отключается, студия живёт).
- Правило производительности: SDK-события — для редких фактов (выделение изменилось,
  документ сохранён); per-frame пути (жесты, рендер) не выходят за границы контрола.

#### Обработка сбоев плагинов

- Все вызовы хост→плагин (активация, команды, построение окон, drawer'ы) идут через
  шов Extensibility с перехватом: исключение логируется с атрибуцией к плагину,
  показывается уведомление; повторные сбои → плагин помечается неисправным и
  автоматически отключается (внешний — с выгрузкой ALC).
- Контент ToolWindow вставляется в дерево не напрямую, а через защитный контейнер
  Shell, перехватывающий исключения layout-прохода: упавшая панель заменяется
  заглушкой «панель аварийно завершилась · подробности · Reload», остальная студия
  работает (Avalonia сама контролы не изолирует).
- Глобальные обработчики: необработанные исключения UI-потока и unobserved Task —
  ловим, атрибутируем к плагину по стеку/ALC, логируем, помечаем плагин.
- Правки документов — транзакциями `IUndoService`: исключение посреди правки
  откатывает её, документ не остаётся полуизменённым.
- От фатальных сбоев процесса (StackOverflow, OOM, native-краш, зависание UI-потока)
  in-proc модель не защищает — осознанная цена, как у Unity/Rider/VS.
- Этап 2: crash reporter + safe mode («прошлый сеанс упал, подозревается плагин X —
  отключить?»), watchdog зависшего UI-потока. Цену краша уже в v1 снижает
  автосохранение.

### Инспектор

Задуман отдельной библиотекой, а вышел частью модуля дизайнера
(`ArxisStudio.Modules.Designer/Inspector`): всё, что он умеет, он умеет про
выбранный на канве узел, и отдельно от канвы у него не оказалось ни одного
пользователя. Своя библиотека понадобится, когда инспектировать начнут не только
разметку.

Модуль дизайнера удалён 2026-08-28 (этап 17) — раздел остаётся записью решения,
а не описанием кода.

- Обход `AvaloniaProperty` + CLR-свойств выбранного контрола, категории
  (Layout / Appearance / Content & Interaction, как в мокапе).
- Встроенные редакторы: число, строка, bool, enum-сегменты, `Thickness`, цвет/`Brush`,
  индикатор binding.
- Реестр `PropertyDrawer`/`CustomInspector` из SDK.
- Запись значений — через абстракцию цели редактирования; приложение адаптирует её к
  Markup (структура/свойства → XAML) и DesignEditor (геометрия), чтобы всё попадало в undo.
  Inspector сам не зависит от Markup/DesignEditor.

### ArxisStudio.Shell

- Зоны tool window (left / right / bottom / center), сплиттеры, сворачивание, вкладки зон.
- Меню и тулбары, собираемые из contributions SDK.
- Строится целиком на ArxisStudio.Controls; тему (ArxisStudio.Themes.Arxis) подключает
  приложение. Переключение dark/light — смена варианта темы.
- Хранилище настроек, каркас локализации, статус-бар.

### ArxisStudio (оболочка)

- **Welcome**: Projects (recents, Open, создание из dotnet new шаблонов; Clone from Git —
  по возможности), Templates (галерея обнаруженных шаблонов), Learn (статика),
  Plugins (менеджер), Settings (тема, язык, поведение).
- **Editor**: зоны, вкладки документов, заголовок, статус-бар — и ни одной панели.
  Наполняют их плагины через контракт SDK; встроенных модулей в репозитории
  больше нет.

35. **Зависимости между плагинами — шаг 1** ✅ *(2026-08-29)*: плагины
   дотягивались друг до друга командами и пунктами меню, и обе щели работали
   как повезёт — порядок подъёма был сортировкой каталога по отображаемому
   имени, то есть по языку интерфейса, Invoke из кода не будил спящего

   спрашивали, а перезагрузка зависимости оставляла зависимых держать её
   прежние типы.
   Манифест объявляет `dependencies`: идентификатор, нижняя граница `min` и
   `optional`. Только нижняя граница — диапазоны заводят для экосистемы, а

   поднять его раньше меня; больше ничего.

   Отказ заразителен по обязательным рёбрам и несёт цепочку причин («B не
   поднят: нужен A, а тот не поднят: нужен C 2.0, установлен 1.0») —
   человеку нужна первопричина. Цикл называет сам путь. Порядок
   детерминированный: топология, внутри уровня модули первыми, затем
   идентификаторы Ordinal — и никогда отображаемое имя. Отказанный не ждёт
   событий: будить его нечем и незачем.
   Нетерпеливый тянет отложенную зависимость при старте; Activate поднимает
   цепочку — зависимости первыми, просимый последним. Invoke будит хозяина
   из самого реестра: дорога у меню и у чужого кода одна. Вне потока
   интерфейса подъём откладывается, тот Invoke честно возвращает false.
   Попутно закрыт изъян: команды при перезагрузке снимались по свежему
   манифесту, и убранная новой версией висела с обработчиком выгруженного

36. **Контрактные сборки и экспорты — шаг 2 зависимостей** ✅ *(2026-08-29)*:
   тип в .NET — имя внутри сборки, загруженной в конкретный контекст, и
   интерфейс, загруженный в контексты двух плагинов, — два разных типа:
   приведение падает с бессмысленным «IFoo не приводится к IFoo». Плагины
   из-за этого обменивались только командами по строке.
   Манифест получил `provides.contracts`: сборки, которые студия загружает
   один раз в общий контекст — как SDK и контролы — и раздаёт всем
   контекстам плагинов по имени, вперёд их собственных копий: даже забытая
   в bin потребителя копия не раскалывает тип.
   Правила, названные заранее. Контракт **не выгружается** до конца
   процесса: обновивший его автор слышит от перезагрузки «студия держит
   прежнюю копию до перезапуска». Объявленный и отсутствующий файлом
   контракт — отказ владельцу до загрузки. Грузится теневая копия — общий
   контекст держит файл, и без неё автор не пересобрал бы плагин при
   открытой студии. Сборка, уже живущая в общем контексте, усыновляется.
   Контракты грузятся до первого подъёма у всех включённых — и у отложенных,
   и у плагинов без entry: типы должны существовать к моменту, когда их
   коснётся любой сосед. Контракт держат тощим: одни интерфейсы, отдельной
   сборкой — чем меньше в нём меняется, тем реже перезапуск. Потребитель
   подключает его с `Private=false`: возит контракт владелец.
   Поверх — `IStudioExports` (Publish/Get через GetService): публикация
   знает хозяина и снимается при его выгрузке, как команды; занятый тип
   второму поставщику не отдаётся, о попытке сказано; своя повторная
   публикация — обновление, не гонка. Потребителю — правило «взял,
   использовал, отпустил»: придержанный объект после перезагрузки соседа —
   его прежняя выгруженная копия.
   Пример: `Arxis.Hello.Contracts` с `IGreeter`; Hello реализует и
   публикует, Friend берёт типизированно. Тест доказывает идентичность
   буквально — приводит объект плагина к интерфейсу, на который ссылается
   сам. SDK 2.2. 252 теста.
   Чего намеренно нет: версионирования контрактов отдельно от плагина;
   обёрток-«швов» вокруг взятых реализаций (сбой внутри прилетает берущему
   обычным исключением, необработанный припишется виновнику по стеку);
   выгружаемых контрактов через цепочки контекстов — та модель не спасает от
   невыгружаемости, но делает граф загрузки необъяснимым; проверки «тощести»
   контракта при упаковке — её держит пример и документация.

37. **Разбор шага 2 и правки по нему** ✅ *(2026-08-29)*: многоугольный
   обзор нашёл в контрактах и экспортах пятнадцать изъянов, два из которых
   воспроизвелись на живом коде как падение студии.
   **Падения.** Плагин, объявивший контрактом не-сборку, ронял
   `LoadStartup` через `BadImageFormatException`, а тот зовётся из
   обработчика `Opened` без перехвата: один чужой файл уносил все плагины и
   модули сразу, и отключить виновника было уже негде. Путь контракта брался
   из манифеста как есть — `Path.Combine` отбрасывает папку плагина для
   абсолютного пути, «..» уводит куда угодно, и произвольный файл грузился в
   общий контекст навсегда, в том числе у языкового пакета, которому
   исполнять нечего. Теперь любая беда с контрактом — отказ владельцу
   записью с ошибкой (правило entry-сборки), а путь обязан остаться внутри
   папки плагина (проверка распаковки архива).
   **Опознание.** Имя контракта читается из манифеста сборки, а не из имени
   файла: резолвер спрашивает по имени сборки, и переименованный файл молча
   не находился бы — тип раскалывался бы там, где контракты его сращивают.
   Общие имена студии под контракт не отдаются, чужая сборка под занятым
   именем отвергается с указанием хозяина: резолвер раздаёт контракт всем
   контекстам раньше прочего, и подмена была бы неотменяемой.
   **Заразительность.** Отказ из-за контракта уходит затравкой в фикспойнт
   графа: зависимый, чьи типы не приехали, раньше поднимался и падал с
   `FileNotFoundException` — исключением, которого не было ни в одном
   перехвате. Оба перехвата подъёма пополнены им и `TypeLoadException`.
   **Уборка.** Записи, заведённые на владельца, снимала оболочка — в двух
   местах из четырёх и разными списками. Снятие упавшего забывало команды
   (отключённый плагин отвечал на них кодом выгруженного контекста),
   `Dispose` не убирал ничего, а опубликовавшийся и упавший на подъёме
   оставлял публикацию навсегда. Теперь хост говорит об уходе событием
   `Unloading`, оболочка подписывается один раз, снятие упавшего идёт через
   `Drop`.
   **Экспорты.** `Publish` проверяет, что реализация того типа и что тип
   живёт в общем контексте: `Publish(new Greeter(ctx))` выводил T из

   «Сохранить как» и смена набора складывали набор из дерева и дома документов,
   а окна не клали. Человек уходил посмотреть соседний набор — и, вернувшись, не
   находил расставленных окон. Теперь сборка набора одна на всех
   (`Current`): забыть окна стало негде. Тремя переключениями подряд живьём
   проверено, что каждый набор возвращает **своё**, а не соседское.
   Открытие документа не имело охраны, которая есть у панели: документ, уехавший
   в своё окно, просился в главное дерево вторым — тот же «контрол в двух
   местах», от которого падал сброс. Держала только совестливость вызывающего.
   Теперь охрана на месте, у обоих одинаковая.
   «Показать» искало только в главном дереве. Оторванную панель оно не доставало
   вовсе: выбор уходил в пустоту, а окно, стоявшее за спиной у студии, так и
   оставалось за спиной. Теперь ищется держащее дерево, и окно поднимается —
   показать значит показать.
   Забытый набор (`Forget`) и сам сброс проверены отдельно: они уносят свои окна
   верно — общий `Sweep` из записи 50 их уже покрывал, и теория это закрепила.
   Все три изъяна сперва пойманы падающими проверками, потом починены; каждая
   проверка отдельно испытана на способность падать. Живьём пройдено меню
   целиком: отрыв, «сохранить как», две смены набора туда и обратно, удаление
   набора, сброс, перезапуск — студия жива, раскладка на месте. 415 тестов.


52. **Ревью раскладки: пятнадцать находок закрыты** ✅ *(2026-08-31)*: полный
   разбор записи 51 десятью независимыми проходами вскрыл, что правка вылечила
   три случая семейной болезни, а сама семья больше.

   Корень оказался в движке. `Select` и `Remove` возвращали новое дерево всегда —
   даже когда менять было нечего. Дерево у вида — свойство, и присвоение
   перекладывает окно целиком, так что охрана `ReferenceEquals` у обоих правщиков
   никогда не срабатывала. Отсюда две беды разом: просьба показать уже показанную
   вкладку сносила и ставила заново всё окно, унося место, где человек печатал, а
   закрытая вкладка главного окна перекладывала каждое оторванное — включая те, где
   этого имени отродясь не было. Теперь правка, которой нечего менять, возвращает
   то же дерево той же ссылкой, и это закреплено отдельной теорией о самом дереве.
   Заодно ушла перекладка «на всякий случай» из `Edit`: о смене того, что стоит за
   именем, просят прямо — `Add` и `Open` зовут перекладку сами.

   Показ не доставал свёрнутое окно. Свёрнутое окно Avalonia считает видимым, и
   один подъём оставляет его свёрнутым; кнопки на панели задач у оторванного окна
   нет — панель становилась недостижимой совсем. Замерено на живом окне, а не
   выведено: `IsVisible=True State=Minimized` и после `Activate()`. Теперь окно
   разворачивается.

   Показ мёртвого имени объявлял успех. Плагин выключили, место за ним в дереве
   осталось — и оболочка помечала документ показанным и писала его путь в строке
   состояния, хотя на экране не появлялось ничего. Причина была выше: выключение
   плагина по счёту сбоев снимало панели, но документы оставляло в списке
   открытых — не так, как это делает перезагрузка. Теперь оба пути одинаковы, а
   раскладка о мёртвом имени молчит.

   `Showing` знал одно главное дерево. Стоило документам уехать в свои окна — и
   оболочка, закрыв соседа, будила не тот редактор, а закрыв последний, не будила
   никого. Это был четвёртый член той же семьи, и правка 51 его не тронула.
   Чтобы пятого не было, заведён общий примитив: `Edit(имя, правка)` — «правь то
   дерево, где имя стоит». Через него теперь идут и показ, и уборка; прежде это
   было написано в классе тремя разными способами.

   Ещё шесть находок — давние, но правка 51 их расширяла или выводила на глаза:
   набор уносил с собой окно-призрак, оставшееся без единого имени, и копировал
   его в каждый новый набор (прежний код призрака попутно вычищал — теперь окно
   просто закрывается); уборка имени не прибирала опустевшее окно, и на экране
   оставалась пустая рамка с именем только что закрытого документа; размер
   оторванного окна не доходил до файла — про переезд спрашивали, про размер нет;
   документ, вернувшийся из закрытого окна, заводил себе группу по слову
   «documents», не глядя на то, где дом документов на самом деле; и `null` посреди
   списка окон ронял студию на старте разыменованием, которого не ловит ни разбор,
   ни хранилище.

   Последнее проверено живьём в обе стороны: с дырявым файлом студия падает
   необработанным исключением на открытии проекта, с правкой — открывает тот же
   файл и живёт. Размер окна тоже: потянули угол — 420×320 стало 582×442 в файле.

   Две теории пришлось переписать: одна не могла упасть (набор запоминался до
   отрыва, и проверять было нечего), вторая мерила не то (раскладку пометил
   изменившейся сам отрыв, и запись доходила до файла без спросу). Каждая из
   четырнадцати правок отдельно испытана мутацией. 430 тестов.


53. **Полоса вкладок стала заголовком оторванного окна** ✅ *(2026-09-01)*:
   у оторванного окна было две шапки одна над другой — пустая полоса заголовка
   38 пикселей и полоса вкладок ещё 38. Промерено на живом окне: 76 пикселей

   вкладок, а сама полоса взяла на себя её работу — за пустое место окно двигают,
   двойным щелчком разворачивают. Так же это устроено и у Unity, и по той же
   причине: у окна с одной панелью подпись вкладки и есть имя окна, а второй раз

   конфигурация, переключатель темы, — а её высота подписана в теме как значение

   стать на экране и завести заново, и тот же контрол просился в две шапки разом.
   Поймано теорией, которая уже была: `A_torn_window_waits_out_its_plugin_hidden`.

## Приложение A — формат каталога модуля и плагина

Один формат манифеста для обоих режимов; отличается только расположение каталога и
способ загрузки сборки.

### Внешний плагин (установленный)

```
%APPDATA%/ArxisStudio/plugins/            ← Windows; Linux/macOS — стандартные пути платформы
  arxis.figma-import/                     ← имя папки = id плагина
    plugin.json                           ← манифест
    bin/
      Arxis.FigmaImport.dll               ← entry-сборка
      Arxis.FigmaImport.pdb
      ThirdParty.Something.dll            ← приватные зависимости плагина
    assets/
      icon.png                            ← значок в менеджере плагинов, PNG 128×128
      preview.png
    lang/
      strings.json                        ← язык, на котором плагин написан
      strings.ru.json                     ← перевод; %key% из манифеста и из кода
    README.md
    CHANGELOG.md
```

В `bin/` не должно быть общих сборок студии (`ArxisStudio.Sdk`,
`ArxisStudio.Controls`, сборки Avalonia) — резолвер всегда берёт их из default
ALC; таргет упаковки это контролирует. Под этими именами нельзя объявить и
контракт: студия такой манифест отвергает.

Собственная контрактная сборка плагина (`provides.contracts`) — исключение и
обязана лежать именно в `bin/`: студия грузит её оттуда в общий контекст сама.
Потребитель чужого контракта подключает его с `Private="false"` — возит
контракт владелец, а копия в чужом `bin/` всё равно будет отвергнута в пользу
общей.

### Языковой пакет

```
%APPDATA%/ArxisStudio/plugins/
  arxis.lang-de/
    plugin.json                          ← только contributions.languages
    lang/
      de.json                            ← ключи студии, значения на языке пакета
      arxis.hello.de.json                ← перевод чужого плагина, необязателен
```

```json
"languages": [ {
  "code": "de", "name": "Deutsch", "file": "lang/de.json",
  "translations": [ { "id": "arxis.hello", "file": "lang/arxis.hello.de.json" } ]
} ]
```

Свой перевод плагина сильнее перевода из пакета: про свой продукт автор
знает больше постороннего.

Ни `entry`, ни `activation`: сборки в пакете нет, поднимать нечего. Ставится
и обновляется тем же менеджером и тем же `.axplugin`, что и обычный плагин.

Начинают не с чистого листа:

```bash
dotnet new install templates/Arxis.Language
dotnet new arxis-language -n de --display Deutsch
```

Готовый пример пакета лежит в `src/Plugins/Arxis.Lang.De`: часть строк студии,
перевод плагина `arxis.hello` и согласованное название ветки меню. Шаблон и
пример видны в решении отдельными папками — править их можно прямо из среды.

### plugin.json

```json
{
  "id": "arxis.figma-import",
  "name": "Figma Import",
  "version": "2.4.0",
  "publisher": "Arxis Labs",
  "description": "Импорт макетов Figma в дизайнер форм",
  "icon": "assets/icon.png",
  "sdk": { "min": "1.0" },
  "entry": "bin/Arxis.FigmaImport.dll",
  "contributions": {
    "commands":    [ { "id": "figma.import" } ],
    "menus":       [ { "path": "Tools/Figma/Import…", "command": "figma.import" } ],
    "toolWindows": [
      {
        "id": "figma.panel",
        "title": "Figma",
        "placement": { "side": "right", "size": 0.24, "near": "arxis.git:git.changes" }
      }
    ],
    "settings":    [ { "key": "figma.apiToken", "type": "string", "scope": "user",
                       "title": "Токен Figma", "default": "" } ],
    "languages":   [ { "code": "de", "name": "Deutsch", "file": "lang/de.json" } ]
  },
  "dependencies": [
    { "id": "arxis.git", "min": "1.2" },
    { "id": "arxis.icons", "optional": true }
  ],
  "provides": {
    "contracts": [ "bin/Arxis.FigmaImport.Contracts.dll" ]
  },
  "activation": [ "onCommand:figma.import", "onFileType:.fig", "onToolWindow:figma.panel" ]
}
```

Всё из `contributions` хост показывает (меню, Settings, ассоциации файлов), не загружая
сборку; сборка грузится при первом событии `activation`. Атрибуты (`[Command]`,
`[CustomInspector]`, …) действуют внутри сборки после активации. Для плагина «из одного
класса» допускается `"activation": ["onStartup"]` — минимальный манифест, всё объявляют
атрибуты, но такой плагин платит временем старта.

### Встроенный модуль (в главном репо)

```
src/Modules/
  ArxisStudio.Modules.Hierarchy/
    module.json                           ← тот же формат манифеста (без bin/)
    ArxisStudio.Modules.Hierarchy.csproj  ← ProjectReference на Sdk, Controls; default ALC
    HierarchyToolWindow.cs
    Assets/…
    Lang/…
```

`module.json` встраивается как embedded resource; Extensibility читает манифесты
встроенных модулей из ресурсов, внешних — с диска, дальше конвейер один. Перенос
модуля во внешний плагин = переложить каталог + собрать `.axplugin`; код не меняется.

### Проект автора плагина (dev-time)

Обычный `csproj` со ссылкой на `ArxisStudio.Sdk` (анализатор «только Ax*-виджеты»
приходит с ним) и строкой импорта таргета упаковки:

```xml
<Import Project="путь/к/src/ArxisStudio.Sdk/build/ArxisStudio.Sdk.targets"/>
```

Дальше `dotnet build` сам раскладывает выход в формат каталога рядом с проектом.
Свойства:

| Свойство | По умолчанию | Что делает |
|---|---|---|
| `AxPluginManifest` | `plugin.json` рядом с проектом | где лежит манифест |
| `AxPluginId` | из манифеста | имя архива и папки установки |
| `AxPluginPackageDir` | `package/` | куда раскладывать |
| `AxPluginArchive` | `<id>.axplugin` рядом с проектом | куда паковать |
| `AxPluginPack` | `false` | паковать ли |
| `AxPluginDeploy` | `false` | класть ли в папку плагинов студии |

Выкладка идёт мимо менеджера плагинов — он отказывается ставить поверх
установленного, а отладке нужно ровно обратное. Три следствия: студию перед этим
надо закрыть (она держит сборки открытыми), папка заменяется целиком, а
выключённым плагин останется и после выкладки — это записано не в его папке, а в
`.disabled.json` рядом.
